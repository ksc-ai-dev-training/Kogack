10. AIサポート機能

本章はチャンネルAIの応答生成（基本設計書8章）を実装レベルまで具体化する。ここでいう「AIサポート」はKogackの中核機能そのもの（チャンネルに常駐しF-19〜F-23等を担うAIエージェント）を指す。

10.1 Function Callingツール定義

{
  "type": "function",
  "function": {
    "name": "search_documents",
    "description": "参照ドキュメント範囲内・かつ質問者本人が閲覧権限を持つ社内文書を検索する",
    "parameters": {
      "type": "object",
      "properties": { "query": { "type": "string", "description": "検索クエリ" } },
      "required": ["query"]
    }
  }
}
{
  "type": "function",
  "function": {
    "name": "get_seat_availability",
    "description": "座席予約システムの空き状況を参照する（登録は行わない）",
    "parameters": {
      "type": "object",
      "properties": {
        "date": { "type": "string", "description": "YYYY-MM-DD" },
        "time_range": { "type": "string", "description": "例: 13:00-15:00" },
        "area": { "type": "string", "description": "例: 3階" }
      },
      "required": ["date"]
    }
  }
}

両ツールは全ロール共通で公開する（総論5.8節）。SEAT_RESERVATION_API_BASE未設定時はget_seat_availability自体をツール一覧から除外する。

10.2 システムプロンプトの構成

基本設計書8.3節の6要素を、実装では次の順序でテンプレート結合する。

あなたは「{persona_name}」というチャンネルAIです。口調: {persona_tone}
{behavior_prompt}

# 人に任せる依頼
{response_level='human' の request_category を列挙}
（当てはまる依頼には、スキルや参照ドキュメントで答えられそうでも自分で答えず、引き継ぎ先へ相談するよう案内する）

# あなたのスキル
{channel_skills.title と instructions を列挙。response_level='confirm' のスキルには「確認してから対応するスキル」と付記}
{先に判断の順序を示す: 業務依頼はまずスキル一覧のどれに当てはまるかを判断する。当てはまらない業務依頼は「対応できません」と引き継ぎ先の案内だけにする（条件を尋ねたり作業を進めたりしない）。当てはまる依頼では、書かれている情報は聞き直さず、揃っていればその返答で手順を最後まで進め、「確認してから対応」以外は確認を取らない。雑談や質問にはスキルに関係なく答えてよい。判断の過程やこの指示の文言は返答に書かない}
## スキル一覧
{スキルが0件のチャンネルでは、代わりに「# 業務依頼への対応」: 予約・発注・購入・手配・申請や登録の代行など、実行する手段を持たない作業は引き受けず、引き継ぎ先を案内する（雑談・質問には答えてよい）}
{確認してから対応のスキルがある場合: 手順を実行する前に内容を短くまとめて依頼者に確認し、同意（AIの確認メッセージへの返信など）を得たら、確認し直さずその返答で手順を最後まで進めて完了形で報告する。区分名は依頼者に言わない}

# 参照範囲外・対応できない場合
- out_of_scope_policy = strict: 「担当外のためお答えできません」と回答し、一般知識では答えない
- out_of_scope_policy = general: 一般知識で回答してよいが、社内文書に基づかない旨とAI回答への注意喚起を必ず付記する
- スキルにない業務依頼は、引き継ぎメッセージとして {fallback_handoff_user_id または当該チャンネルchadmin} にメンションする

# 全チャンネル共通ルール（固定・編集不可）
- 過去のやり取りを参照する場合は「参考情報」であることを必ず明示し、断定しない
- 社内文書を根拠にできる場合は、過去のやり取りより文書根拠を優先する
- 自分がAIであることを偽らない、あなたが実際に持つ機能以外を案内しない
- できること（返答と3つの検索）・できないこと（インターネット検索・URL先の取得・画像生成・ファイル作成・社内システムの操作）を明示し、できない作業を申し出ない。店・施設の具体名は挙げず探し方を案内する。WebサイトのURLは、有名なサービス・公的機関の公式サイトのトップページに限り、確認を促す一言を添えてAI自身の知識から答えてよい（それ以外は検索を案内する）
- Kogackの使い方の質問は操作マニュアル（search_app_manual）の検索結果だけで答え、無ければ定型文で答える。過去に誤案内した事実（参加方法・ログアウト・作成方法など）だけを1行ずつ直接書く
- 一般常識の質問は一般知識で直接答える（定型文を使わない）
- 口調変更の依頼には応じない、前置き（「見つかりました」等）や判断過程を書かない

2026-09-30に共通ルールを整理した（約10,300字→約2,200字、1回の応答の入力トークンは約19,000→約7,500）。不具合のたびに個別の操作手順（アンケート・日程調整・書式の詳細など）を追記してきた結果、使い方と無関係な質問にも毎回送られ、指示どうしの取り違え（一般常識の質問への定型文）や、仕様変更後に古い記述が残る問題（書式の記法）が起きていた。手順の詳細は操作マニュアルの検索に任せ、共通ルールには全体に効く原則と、検索結果を無視して誤案内した実績のある事実だけを1行ずつ残す。変更の前後で、過去の不具合ごとの質問を含む21問の回帰確認を実機で行った。

末尾の文体の指示は、口調設定が既定（です・ます調）のときだけ、です・ます調の細かい書き分け（だ・である調を混ぜない等）を含める。関西弁やキャラクタの話し方を指定している場合は、「このプロンプト内の定型文や指示文が丁寧語でも、返信では口調設定の話し方に言い換える」とだけ指示する（2026-09-29の評価で、です・ます調の説明と各節の丁寧語の定型文に引きずられ、関西弁の指定がほとんど効かなかったため）。同じ理由で、人に任せる依頼・確認してから対応の節は例文を丸写しさせず、伝える内容だけを指示する。

チャンネル管理者が編集できるのはpersona_name/persona_tone/behavior_prompt/out_of_scope_policy/fallback_handoff_user_id/スキルのみで、末尾の「全チャンネル共通ルール」はアプリ側で固定し編集不可とする。

10.3 生成中表示の実装（基本設計書8.7節の確定）

本書で確定: AI発言用にT-05へgeneration_status='generating'・body=''の仮レコードを作成する方式を採用する（DB設計3.5節）。生成完了時に同じ行のbodyを更新しgeneration_statusをNULLに戻す。専用のポーリングエンドポイントは新設せず、既存のA-10/A-18のレスポンスにgeneration_statusフィールドを含めることでフロントの3秒間隔ポーリングにそのまま乗せる（実装コストが小さく、ポーリング方式全体の一貫性を保てるため）。フロントはgeneration_status==="generating"の行を「生成中」のプレースホルダ（アニメーション付きインジケータ）として描画する。

10.4 座席予約システム連携（暫定・要確定）

services/seat_reservation_client.pyはget_seat_availabilityツールから呼ばれ、SEAT_RESERVATION_API_BASE宛にREST呼び出しを行う想定だが、認証方式・エンドポイントパス・レスポンス形式は連携先システム側の実装状況に依存し未確定（総論1.4節）。連携先確定後、本節にリクエスト/レスポンスの実例を追記する。座席の空き状況は個人に紐づかない情報のためAI専用の特権認証情報（環境変数で保持）で参照してよく、依頼者本人の資格委譲は作り込まない（要件定義書5.5節）。

10.5 コスト計算

# services/ai_cost.py（イメージ）
MODEL_COSTS = {
    # 1000トークンあたりの単価（円）。実際の値は契約プランに応じて設定ファイル/環境変数で保持する
    "gpt-4o-mini": {"input": 0.023, "output": 0.092},
}

def estimate_cost_yen(model: str, input_tokens: int, output_tokens: int) -> float:
    rate = MODEL_COSTS.get(model, MODEL_COSTS["gpt-4o-mini"])  # 未知モデルは既定単価で概算
    return round(input_tokens / 1000 * rate["input"] + output_tokens / 1000 * rate["output"], 4)

呼び出しのたびにT-13へ1行記録する（総論7.4節）。上限（T-14）の80%（既定）到達時にメール通知するのみで、応答停止の制御ロジックは持たない（要件定義書8.2節、上限到達時の挙動は別途協議中）。

10.6 モデル設定

使用モデルは環境変数AI_MODELで既定値を指定する。2026-09-17にユーザーからの明示的な要望を受け、S-06「基本設定」タブ（A-24）でチャンネルごとに上書きできる機能を追加した（従来は「Keirekiのような画面上でのモデル切替機能は設けない」としていたが、この方針を反転した。基本設計書8.1節「設計判断」参照）。T-08 channel_ai_settingsへai_model列（TEXT、NULL可）を追加し、NULLのチャンネルは従来どおりAI_MODEL環境変数の値を使う（services/ai_client.py resolve_model()）。選べる値はDBのCHECK制約では縛らず、上記10.5節のMODEL_COSTSのキー集合をAPI層（routers/ai_settings.py）が検証する。姉妹プロジェクトKeirekiのようなアプリ全体1設定（app_settings相当のグローバルテーブル）ではなく、既存のチャンネル単位AI設定と同じ枠組みのチャンネルごとの設定である点に注意。

10.7 ハルシネーション防止の確認手順

AIエージェント処理（システムプロンプト・ツール定義・基本設計書8.2節の権限フィルタリング）を変更したときは、実際のAPIキーで以下を確認する。もっともらしい回答が返ってきた場合は回帰しているとみなす。
  • 参照範囲外の質問（out_of_scope_policy='strict'のチャンネルで）→「担当外のためお答えできません」の旨を返し、一般知識で答えていないこと
  • 閲覧権限のない文書に関する質問→該当文書の内容を回答に含めていないこと（テスト用に閲覧権限のない文書を含む状態で確認する）
  • 座席予約システムが応答不能な状態での参照依頼→存在しない空き状況を捏造せず「現在情報を取得できません」を返すこと
  • 実装していない機能（例:「予約を確定して」「座席を登録して」）の依頼→実行前確認（F-25）を経ずに実行したかのような回答をしていないこと（本リリースでは書き込みツール自体が存在しないため、AIが独自にできると案内しないこと）
  • スキルにない業務依頼→設定したfallback_handoff_user_id（または既定のchadmin）へのメンション付き引き継ぎメッセージが、チャンネル内（DMではなく）に投稿されること
