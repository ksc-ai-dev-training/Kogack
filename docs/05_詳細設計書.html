1. はじめに

1.1 本書の位置づけ

本書は、AIネイティブチャットシステム（コードネーム: Kogack）の詳細設計書（総論）である。基本設計書で定めたシステム構成・画面・機能・データベース・API・AIエージェント・非機能の各方針を、実装者がそのまま手を動かせる粒度まで具体化する。カラム単位のテーブル定義、リクエスト/レスポンスのフィールド定義、権限判定の実装方式、検索SQLの方針、エラー時の挙動、画面項目の入力規則、代表的な処理のシーケンス、AIプロンプト・ツール定義の実体を定める（詳細はDB設計・API設計・画面設計・AIサポートの各分冊）。

基本設計書が「方式」を決める文書であるのに対し、本書は「その方式を具体的にどう実装するか」を決める文書である。基本設計書8.7節のように基本設計書側で「詳細設計書で確定する」と明記されていた論点は、本書該当節（AIサポート10.3節）で確定する。

1.2 前提ドキュメント

本書は要求仕様書・要件定義書・基本設計書・画面モックアップを前提とする。ID体系（REQ-xx / F-xx / S-xx / T-xx / A-xx）は基本設計書までと共通のまま用い、本書で新たにIDを増やすことはしない（本書は既存IDの実装詳細を追記する文書であり、機能追加は行わない）。

1.3 対象読者

  • 本システムの実装を担当する開発者（本書を実装のリファレンスとする）
  • コードレビュー担当者（実装が本書の定義から逸脱していないかの確認）
  • AI開発研修の受講者（設計から実装への橋渡しのサンプルとして参照）

1.4 本書のスコープ外

座席予約システムとの実際の連携仕様（認証方式・エンドポイント・レスポンス形式）は、連携先システム側の実装状況に依存する外部要因であり、確定していない（要件定義書8.2節・基本設計書8.4節）。本書AIサポート10.4節は現時点で合意可能な範囲（Function Callingツールのインタフェース・呼び出し方）のみを定め、連携先固有の仕様は連携先確定後に本書を改訂して追記する。

また、本番運用の監視・アラート設定の細則、CI/CDパイプラインの具体的な設定ファイル、負荷試験の計画は本書の対象外とする。

2.3 スキーマ変更の運用

本書で確定: database.py の SCHEMA は CREATE TABLE IF NOT EXISTS で構成するため、既存テーブルへの列追加は起動時に自動適用されない。列を追加する変更は ALTER TABLE ... ADD COLUMN IF NOT EXISTS を SCHEMA に併記すること。開発環境（AUTO_MIGRATE=1）は起動時に流れるが、本番（AUTO_MIGRATE=0）はSupabase上で手動実行が必要になる。忘れると該当APIが column ... does not exist で失敗するため、テーブル定義（DB設計3章）を変更する改訂では必ずこの手順をあわせて確認する。

2.4 コーディング規約

  • バックエンド: 全エンドポイントを async def で実装し、DBアクセスは asyncpg を直接使用する（ORMは用いない、LCC CRM踏襲）。関数・変数は snake_case。
  • フロントエンド: 関数コンポーネント＋hooksのみを用いる（クラスコンポーネントは使わない）。API呼び出しは lib/ のクライアント経由に統一し、コンポーネントから直接 fetch しない。
  • ID体系: すべてのAPIレスポンスで id は文字列（string）としてシリアライズする。BIGINTはJavaScriptの安全な整数範囲（2^53-1）を超えうるため、フロントエンドでの丸め誤差を避ける（API設計4.1節）。
  • 日時: すべてUTCのISO 8601（2026-08-21T09:00:00Z）でやり取りし、表示側でローカルタイムゾーンに変換する。

5. 権限制御詳細

5.1 権限デコレーター

auth_helpers.py に以下のデコレーター/依存関数を用意し、各ルーターで組み合わせて使う。判定はすべてサーバー側で行い、フロントの表示制御には依存しない（REQ-N-02）。

5.2 API別の権限判定実装

基本設計書3.3節の権限マトリクスをAPI単位に落とし込む。原則は次の3パターンに集約される。

  • チャンネル参加者限定（発言本文を扱うA-10〜A-15, A-69, A-72等）: require_channel_member を適用。adminであっても非参加の非公開チャンネルでは404（会話内容は参加者限定のまま）。
  • チャンネルのメタデータ限定（発言本文を含まないA-06, A-46）: require_channel_member_or_admin を適用。adminは非参加の非公開チャンネルでもメタデータ（チャンネル名・説明・参加者一覧）を取得できる（5.9節「設計判断」参照）。
  • 当該chadmin/admin限定（A-09, A-23〜A-31, A-45, A-47〜A-56, A-63〜A-66）: require_channel_admin を適用。「自分が担当するチャンネルのみ編集可、担当外は不可（adminは全チャンネル可）」の判定を1関数に集約する。
  • admin限定（A-36〜A-44）: require_admin を適用。

5.3 非公開チャンネルの可視性（F-34）

未参加の非公開チャンネルに対するAPIアクセス（A-06, A-10等）は403ではなく404を返す。403は「チャンネルの存在は分かるが権限がない」ことを意味してしまい、非公開チャンネルの存在自体を露呈させないという要件（F-34「参加していない者には一覧・検索に表示されない」）に反するため。require_channel_memberはこの区別（存在しない/公開だが未参加=403/非公開かつ未参加=404）をAPI一律で行う。

A-05（チャンネル一覧）のクエリは、次の2つを合成して返す。

-- 参加中チャンネル
SELECT c.* FROM channels c JOIN channel_members m ON m.channel_id = c.id WHERE m.user_id = :me
-- 参加可能な「公開」チャンネル（非公開は含めない）
SELECT c.* FROM channels c
WHERE c.is_public = true AND c.id NOT IN (SELECT channel_id FROM channel_members WHERE user_id = :me)

5.4 非公開チャンネルへのメンバー追加（A-08）

非公開チャンネルへの追加は「chadmin限定」ではなく「参加者なら誰でも」に開放する（基本設計書6.2節「設計判断」）。実装は require_channel_member（chadminではなく一般の参加者チェック）をA-08の非公開分岐に適用する点が、他の設定系APIの「当該chadmin/admin限定」と異なるので注意する。

5.5 最後の1人のチャンネル管理者保護（A-48）

-- A-48 実行前チェック（トランザクション内）
SELECT count(*) FROM channel_members WHERE channel_id = :cid AND is_channel_admin = true;
-- 結果が1、かつ解除対象がその1人なら 400 { "detail": "最後のチャンネル管理者は解除できません" }

5.6 fallback_handoff_user_id・アイコンURLの反映時検証

A-45は指定された fallback_handoff_user_id が当該チャンネルのT-03参加者であることを検証する（400）。対象者が後日退出・無効化された場合は、参照時（AIエージェント処理・A-23取得時）にNULL相当（既定のchadminへ引き継ぎ）として扱う。A-25・A-54・A-55・A-62は、A-61で取得したURLをそのまま信頼せず、自ドメイン（Supabase Storageのicons/パス）のURLであることを検証してから保存する。

5.7 RLSポリシー方針

アプリケーションはasyncpgで直接接続するためアクセス制御の主体は上記のAPI層だが、Supabaseの他経路（PostgREST等）からの意図しない参照を遮断する多層防御として全テーブルRLSを有効にする（基本設計書6.3節）。

ALTER TABLE messages ENABLE ROW LEVEL SECURITY;
CREATE POLICY messages_participant_only ON messages FOR SELECT USING (
  (channel_id IS NOT NULL AND EXISTS (
     SELECT 1 FROM channel_members m WHERE m.channel_id = messages.channel_id AND m.user_id = current_setting('app.user_id')::bigint))
  OR
  (dm_id IS NOT NULL AND EXISTS (
     SELECT 1 FROM direct_message_members m WHERE m.dm_id = messages.dm_id AND m.user_id = current_setting('app.user_id')::bigint))
);

ALTER TABLE channels ENABLE ROW LEVEL SECURITY;
CREATE POLICY channels_visibility ON channels FOR SELECT USING (
  is_public = true
  OR EXISTS (SELECT 1 FROM channel_members m WHERE m.channel_id = channels.id AND m.user_id = current_setting('app.user_id')::bigint)
);

同様の参加者限定ポリシーを message_blocks・message_attachments にも適用する。current_setting('app.user_id') の設定方式（セッション変数の注入箇所）はdatabase.pyのコネクション取得処理で統一する。

5.8 AIのドキュメント参照とアプリロールの独立性

Kogackでは、AIが呼び出せるFunction Callingツール（search_documents・get_seat_availability）自体はmember/chadmin/adminいずれのロールでも同一に公開する。ドキュメント検索の絞り込みはアプリロール単位ではなく、質問者個人のGoogle Drive閲覧権限を都度確認する方式（基本設計書8.2節）で行うため、ロールに応じたツールの出し分けは不要かつ行わない。これは「ロールでツール自体を出し分ける」設計（例えば一般ユーザーにはツールを渡さない方式）とは異なる考え方であり、AIサポート10.1節で改めて扱う。

5.9 フロントエンドの権限外アクセス時の挙動（App.tsx ルートガード）

S-06・S-08等のURLを直接入力した場合の挙動（基本設計書4.2節「設計判断」）を、App.tsxのルートガードの実装レベルで確定する。各ルートのローダーは、そのルートの表示に最低限必要なAPI（下表）を呼び出し、レスポンスのステータスコードに応じて分岐する。フロント側でrole/is_channel_adminを事前判定して描画を止めることはしない（判定はAPIレスポンスを正とする。5.1節「判定はすべてサーバー側で行い、フロントの表示制御には依存しない」の原則どおり）。

設計判断（S-03/S-04には403分岐が無い理由）: S-03/S-04のガードAPI（A-06）はrequire_channel_memberのみを適用し、chadmin等の追加権限は問わない。公開チャンネルは誰でも即座に参加できる（F-02）ため、「参加していないと見えない」という制約自体はあるが「参加した上でさらに見えない」状態は無く、A-06が返すのは404（非公開・非参加）のみである（5.3節）。403分岐を表に残しているのは、将来S-03/S-04にchadmin限定の表示要素が追加された場合の拡張余地を示すためで、現時点では到達しない分岐として扱う。
設計判断（システム管理者が非参加の非公開チャンネルでS-06を開けるようにした理由）: 要件定義書の権限マトリクスは、チャンネルの削除・名称編集・公開範囲切替・AI設定編集をいずれもadmin「○（全チャンネル）」としており、この権限マトリクス上の意図はrequire_channel_admin（A-09, A-23〜A-31, A-45, A-47〜A-56, A-63〜A-66）のadminバイパスとして実装済みだった。しかし本節の表が示すとおりChannelSettings.tsxはS-06自体の許可判定にA-23を使う一方、画面ヘッダーの表示（チャンネル名）とチャンネル管理者タブ（名称・説明編集フォームの初期値、参加者一覧、chadmin追加解除）のためにA-06・A-46も呼んでおり、この2つはrequire_channel_member（adminバイパス無し）のままだったため、一度も参加していない非公開チャンネルではS-06自体が開けなかった（実装当時の既知の制約として2026-08-26付でCLAUDE.mdに記録）。A-06・A-46はいずれも発言本文を一切含まないメタデータ専用エンドポイントであるため、この2つに限定してrequire_channel_member_or_admin（5.1節）へ切り替えても、要件定義書が別途明記する「参加していない非公開チャンネルの会話内容は既定で見えない」という制約（3.3節権限マトリクス「非公開チャンネルの一覧表示・検索・閲覧」行）は崩れない。実際、発言本文を扱うA-10〜A-15・A-69・A-72はrequire_channel_memberのままadminバイパスを持たないため、システム管理者がS-03（この画面）を直接開いても会話内容は見えない。当初はchannelErrorの404/403時（5.9節、F-34「存在を伏せる」対象）と同じ「ワークスペースへ無言でリダイレクト」を踏襲していたが、S-08管理コンソールのリンク経由でS-06からS-03へ遷移した際に「サイドバー以外真っ白な画面になり何が起きたか分かりづらい」というユーザー指摘を受けて改めた。channel.is_member=falseの時点でA-06自体は既に成功しておりチャンネルの存在・名称はシステム管理者へ開示済み（S-08のリンクを踏んだ以上、伏せる意味が無い）であるため、この分岐に限り無言リダイレクトをやめ、「🔒 {name} には参加していません」という明示的なメッセージとS-06への戻り導線を表示するよう`ChannelView.tsx`を変更した。5.9節の表・上記の「無言でリダイレクト」という原則は、F-34の対象であるchannelErrorの404/403（未参加者から存在を伏せるべきケース）には引き続き適用され、この変更は影響しない。
設計判断（ログイン中のユーザーが実行中に切り替わった場合の保護）: 本節の表・上記の設計判断はいずれも「今表示しようとしているルートに対して、今ログインしている本人が権限を持つか」を判定する話だが、それとは別に「そもそも今このタブに表示されているURLが、今ログインしている本人のものか」という前提自体が崩れるケースが実機検証で見つかった（ユーザーからの報告）。あるユーザーがチャンネル会話を開いたまま、ログイン・ログアウトの各ボタン（navigate()で安全な起点へ遷移する実装済みの経路）を経由しないセッション切り替え（複数タブ・別ブラウザでの再ログイン・dev-loginのAPI直接呼び出し等）が起きると、そのタブは直前のユーザーが見ていたURL（他人のチャンネル）をそのまま新しいユーザーの権限で描画してしまう。新しいユーザーがシステム管理者であれば、上記「非参加の非公開チャンネルでもメタデータを取得できる」設計とあいまって、本来知らないはずの非公開チャンネルの存在・名称が「🔒 {name} には参加していません」の形で意図せず開示される。対策として、App.tsxでuseMe()が返すユーザーIDをアプリ実行中ずっと追跡し、直前と異なる（かつnullでない）IDへ変化した瞬間に、ChannelView等のルート要素を一切描画せず安全な起点（/）へ強制的に戻す（レンダー中にstateを調整するReactの公式パターンを使い、useEffectでnavigate()を呼ぶ実装ではChannelView等が新しいユーザーの権限で一度マウントされてから遅れて是正する形になり、他のフックの再検証と競合すると是正が効かないことがあったため採用した）。あわせて、この切り替え検知が確実に一定時間内（数秒）に働くよう、useMe()にも他の主要フック（usePolling、3秒間隔）と同じrefreshIntervalを持たせた（フォーカス／オンライン復帰イベントだけに頼ると、タブがフォーカスを失わない限り検知されない場合があった）。この対策はチャンネルURLのリークだけでなく、サイドバー（S-02）のDM相手一覧・チャンネル一覧にも同様の問題（直前のユーザーのものが各フック自身の次のポーリングまで残る）があるとユーザーから指摘され、SWRのキャッシュキーがURLのみでユーザーを問わないことが原因と特定した。ユーザーID変化を検知した同じタイミングでSWRのグローバルmutate(() => true, undefined, {revalidate: true})を呼び、全キャッシュ（チャンネル一覧・DM一覧を含む）を即座に再取得することで、切り替わった直後からサイドバーも新しいユーザーのものに揃うようにした。

A-02は失敗時にJSONではなく /login?error=<種別> へリダイレクトし、S-01がクエリパラメータに応じたメッセージを表示する（画面モックアップS-01の「許可ドメイン外のアカウントでログインした場合の表示例」に対応）。

account_disabled該当ユーザーがis_active=false「アカウントが無効化されています。管理者にお問い合わせください。」

7.4 監査ログ・AI利用ログの書き込み

services/audit.py に record_audit(event_type, actor_user_id, target_channel_id, target_field, summary) を用意し、A-02（ログイン成功/失敗）、A-24〜A-27・A-31（AI設定変更）から呼び出す。AI利用ログ（T-13）はservices/ai_agent.pyの応答完了処理からservices/ai_cost.pyを経由して1呼び出しにつき1行記録する（AIサポート10.5節）。いずれも書き込み失敗時に本来の処理（ログイン・AI応答）自体を失敗させない（ログ書き込みはベストエフォート、例外は捕捉してアプリケーションログに出力するのみ）。

7.5 アプリケーションログの方針

  • 構造化ログ（JSON Lines）を標準出力に出し、Fly.io側のログ収集に委ねる（自前のログ基盤は持たない）。
  • 発言本文（messages.body）・振る舞い定義（behavior_prompt）・AIへの質問文/回答文はアプリケーションログに出力しない。 本文はDB（T-05）に既に保存されており、ログへの二重記録は漏えい範囲を不必要に広げるため（AI利用状況ログが質問文・回答文を保存しない方針、基本設計書8.6節と同じ考え方をアプリログにも適用する）。
  • ログに含めてよい情報: リクエストパス・ステータスコード・処理時間・ユーザーID・エラー種別・スタックトレース（本文以外）。

9. 処理シーケンス

9.1 ログイン（Google OAuth）

  1. S-01「Googleでログイン」押下 → ブラウザがA-01へ遷移
  2. FastAPI stateを生成しGoogle認可URLへ302リダイレクト
  3. Google 認証・同意後、認可コード付きでA-02へリダイレクト
  4. FastAPI トークン交換→IDトークン検証→ドメイン照合（NG時7.2節のerror付きで/loginへ）
  5. FastAPI T-01を検索、未登録ならrole='member'で自動登録、is_active=falseなら拒否
  6. FastAPI セッションJWT発行→HttpOnly Cookie→/ へリダイレクト、T-16へログイン結果を記録
  7. SPA A-04→A-05を呼び出し、S-02（サイドバー）を構築して最後に開いていたチャンネルを表示

9.2 メッセージ投稿とAI応答生成（メンション時）

  1. S-03 利用者が「@Kogack AI ...」を送信 → A-11
  2. FastAPI T-05へsender_type='human'で即時保存し201を返す（会話は止まらない、基本設計書8.7節）
  3. FastAPI メンションを検知しservices/ai_agent.pyを非同期タスクとして起動
  4. ai_agent.py T-05へgeneration_status='generating'のAI行を仮作成（body=''）（AIサポート10.3節）
  5. ai_agent.py T-08/T-11/T-12取得、直近履歴取得（F-13上限、基本設計書8.1節）、T-12の区分が「人が対応」ならAI呼び出しをせずchadminへの引き継ぎメッセージを直接投稿して終了（F-17）
  6. ai_agent.py それ以外はシステムプロンプト（AIサポート10.2節）を構成しOpenAI APIをFunction Calling付きで呼び出す
  7. OpenAI API 必要に応じsearch_documents（基本設計書8.2節の権限フィルタリング経由）・get_seat_availabilityを呼び出し、最終回答を生成
  8. ai_agent.py 手順4の行をbody更新・generation_status=NULLに更新し、根拠等をT-07へ保存、T-13へ利用ログを記録
  9. SPA 3秒間隔ポーリング（A-10のsince差分）で新着・更新を検知し表示を更新

9.3 自動応答トリガーの判定（同期・F-38）

  1. A-11 投稿保存後、trigger_matcher.pyを同期呼び出し（sender_type='human'の投稿のみ対象、連鎖防止）
  2. 当該チャンネルのT-21（is_active=true）を取得し、trigger_type/trigger_valueとの部分一致を判定
  3. 一致するルールがあれば、そのままT-05へsender_type='bot', trigger_rule_id=当該ルールIDで新規発言を作成（スレッド内投稿ならthread_parent_idを引き継ぐ）
  4. AIエージェント処理（9.2節）は起動しない（BOT発言はAIの応答対象外）

9.4 送信予約・定期投稿の送信（ディスパッチャ）

  1. アプリ起動時 scheduled_dispatcher.pyをasyncioバックグラウンドタスクとして開始
  2. 30秒間隔でループ: T-18からstatus='pending' AND scheduled_at<=now()を取得し、通常の投稿処理相当でT-05へ発言化、status='sent'に更新
  3. 同ループでT-19からis_active=true AND next_run_at<=now()を取得し、sender_type='bot', recurring_post_id=当該IDでT-05へ発言化、frequencyに応じ次回next_run_atを計算して更新、last_sent_atを更新
  4. 単一インスタンス前提（基本設計書10章）。将来複数インスタンス化する場合はUPDATE ... WHERE status='pending' RETURNING形式のアトミックな取得へ変更する

9.5 ドキュメント質問応答の権限フィルタリング（F-19〜F-21）

  1. 9.2節手順7でsearch_documents(query)が呼ばれる
  2. 索引（基本設計書8.2節、S-08「今すぐ同期」で更新済み）から候補文書を取得
  3. 候補ごとにdrive_client.pyで質問者本人のDrive閲覧権限を確認し、権限なしは除外（キャッシュは数分程度まで許容）
  4. 残った候補のうち当該チャンネルのT-10範囲内のもののみをAIに渡す（範囲外は9.2節のout_of_scope_policyに従う、基本設計書8.2節）
  5. 回答生成後、根拠文書をT-07 message_blocks（citation）として保存

9.6 実行前確認（F-25、本リリースでは到達しない設計上の骨格）

  1. 書き込み系ツールが呼ばれるとT-15へstatus='pending'で登録し、S-03/S-04上にS-07モーダルを表示
  2. 利用者が「実行する」→A-34→status='confirmed'（次フェーズで実際の連携先書き込みに接続）
  3. 利用者が「キャンセル」→A-35→status='cancelled'
