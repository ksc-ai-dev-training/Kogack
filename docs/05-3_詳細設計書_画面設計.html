11. フロントエンドコンポーネント設計

本章はfrontend/src/のReactコンポーネント構成を、責務分割・コンポーネントツリー・各コンポーネントのProps/内部状態・データ取得フック・状態管理方針の観点で定義する。総論2章はディレクトリの役割、本章8節は画面ごとの項目定義を扱うのに対し、本節（11章）は「どのコンポーネントが何を持ち、どう連携するか」を扱う。画面に部品を追加・変更するときは、8章の項目定義とあわせて本章の一覧を更新すること。

本章を新設した理由: 画面モックアップの検討過程で、送信予約（S-03）・メンション候補（S-03、F-41）・検索条件モディファイア（S-05、F-42）・プロフィールカード（S-03、F-40）という4つのポップオーバーを、実装方針を決めないままそれぞれ個別のCSS・開閉ロジックとして作ってしまっていた（見た目・余白・閉じ方が画面ごとに微妙に異なる状態）。同様にDM相手選択（補足02）・メンション候補・検索モディファイアのfrom:/with:は、いずれも「アイコン・氏名・メールアドレス付きの一覧から選ぶ」という同じUIをそれぞれ書いていた。共通化すべき部品を実装前に洗い出しておかないと、同じ挙動をコピペや個別実装で再現することになり見た目・動きが画面ごとにずれる、という反省を踏まえ、実装に入る前の本章でコンポーネント設計を確定する。

11.1 設計方針

方針内容
レイヤー分割pages/（画面＝ルート単位）→ components/（画面横断の部品）→ components/ui/（基礎部品）の3階層。hooks/（データ取得）・lib/（APIクライアント・整形）・types/（API型）はUIを持たない
サーバー状態SWRで取得・キャッシュする（11.4節）。メッセージ一覧（A-10）・DMメッセージ（A-18）はrefreshInterval: 3000のポーリングを既定とする（基本設計書8.1節・9.1節のリアルタイム方針、3秒間隔）。取得ロジックはhooks/のカスタムフックに包み、ページからuseSWRを直接呼ぶのは画面固有で再利用しない取得（S-05の検索結果、S-06各タブの定期投稿/トリガー一覧）に限る
UI状態タブ選択・フォーム入力値・ポップオーバー/モーダル開閉などはコンポーネントローカルのuseStateに置く。Redux / Zustand等のグローバルストアは導入しない（画面間で共有する状態はログインユーザーとチャンネル一覧程度で、SWRのキャッシュで足りるため）
横断的な関心React Contextはトースト通知（ToastProvider）と確認ダイアログ（ConfirmProvider）の2つだけとし、main.tsxでアプリ全体を包む。基本設計書4.2節「設計判断」の権限外リダイレクト時のトーストも、このToastProviderを使う
更新の反映保存系API（PUT/POST/DELETE）の後は、該当フックのmutate()で再取得する（楽観的更新はしない）。ScheduledMessagesModal（補足04）とヘッダーの予約中バッジは同じuseScheduledMessages()を参照するため、キャンセル成功時にmutate()すれば両方が更新される（子がキャッシュキーを個別に持たなくてよい）
Propsの向きデータは親→子へPropsで渡し、子→親はコールバック（onSaved / onClose / onSelect）で通知する。孫以降へのバケツリレーが3段を超える場合のみContext化を検討する（現状は該当なし）
権限による出し分けuseMe()のrole、useChannelMembers()から算出するis_channel_adminで判定する（総論5.1節）。判定箇所はルート（App.tsx、総論5.9節のリダイレクト判定）・メニュー（Layout、adminのみ管理コンソールへの導線を表示）・ボタン（ChannelView、chadmin/adminのみチャンネル設定ボタンを表示）の3箇所に限り、権限の正はサーバー側にある（REQ-N-02）
スタイルTailwind CSSのユーティリティをJSXに直接書く。共通の見た目はcomponents/ui/shared.tsxのクラス生成関数（avatarClass / badgeClass等）に集約し、CSS Modules・styled-componentsは使わない

11.7 APIクライアントとエラー処理（lib/api.ts）

apiFetch<T>(path, init?): credentials: 'same-origin'・Content-Type: application/jsonを既定にしたfetchラッパー（セッションはHttpOnly Cookieのため、JS側でトークンを保持・付与する必要はない）。2xxならJSONをTとして返し（204はundefined）、それ以外はApiError(status, detail)をthrowする。detailは総論7.1節のエラーレスポンス形式から取り、JSONでなければ「エラーが発生しました」とする。

  • 401の共通処理: /api/auth/me以外のパスで401を受けたらwindow.location.href = '/login'でログイン画面に飛ばす（セッション切れ対策）。useMeが使う/api/auth/meは除外し、401を「未ログイン」として扱う（無限リダイレクトを避ける）。
  • 403/404はグローバルには処理しない: 401と異なり、403/404の意味は呼び出し元によって異なる（例: A-13のスレッド取得404は「スレッドが存在しない」、A-06/A-23/A-36の404/403は「権限外パス」を意味しうる）。総論5.9節のルートガード対象API（A-06・A-23・A-36）に限り、呼び出し元（App.tsx）が個別にステータスを見て総論5.9節の表のとおりリダイレクト＋トーストを行う。それ以外のAPIの403/404は、各コンポーネントがエラー表示または空状態表示に使う。
  • apiFetchを使わないケース: ファイルアップロード（A-21添付ファイル、A-61アイコン。FormDataのためContent-Typeを自動設定させる）は生のfetchを使う。この場合も401は個別に処理せず、共通のcheckAuthError()ヘルパーを呼んで同じリダイレクトを行う。

表示の使い分け: 取得失敗（SWRのerror）は画面内にエラーメッセージを表示、保存・削除の結果はuseToast()、破壊的操作（チャンネル削除・発言削除・chadmin解除・予約キャンセル・定期投稿/トリガー削除等）の事前確認はuseConfirm()。alert / window.confirmは使わない。

11.8 コンポーネント追加・変更時の規約

  • 新しい画面（S-xx）はpages/に1ファイルで作り、App.tsxのRoutesとLayoutの導線（サイドバー/ヘッダー）に追加する。ロールで制限する場合はApp.tsxでリダイレクトし（総論5.9節）、同時にサーバー側のガード（総論5.1節）があることを確認する。
  • タブが3つ以上ある画面はpages/<画面>/にタブごとのファイルを分け、親は切替とデータの受け渡し（onSaved等）だけを行う（S-06 / S-08と同じ構造）。
  • 2画面以上で使う部品はcomponents/に、1画面内でしか使わない部品は同じファイル内の非公開コンポーネントにする（exportしない）。
  • ポップオーバー・ユーザー選択・アバター・バッジ・タブが必要になったら、必ずcomponents/ui/の共通部品（11.6節）を使う。新しい表示・入力形式が必要になったらui/に追加し、11.6節の表に追記する（画面ごとの個別実装は禁止。11.1節「共通化」方針）。
  • APIを追加したらtypes/index.tsにレスポンス型を追加し、2つ以上のコンポーネントから参照するならhooks/にフックを作る（11.4節の基準）。
  • localStorageにキーを追加するときはkogack-プレフィックスを付け、11.5節の表に登録する。個人情報・会話内容・フォーム入力値は保存しない。
  • コンポーネントの冒頭コメントに対応する画面IDと本書の章番号を書く（例: // S-03 チャンネル会話（詳細設計書 画面設計11.3節））。
  • 新しいAPIの403/404がロール限定画面のガードを兼ねる場合（S-06・S-08と同種の画面を追加する場合）は、総論5.9節の表にルートを追加する。
