4. API詳細設計

4.1 共通仕様

項目仕様
ベースパス/api。認証はセッションJWT（HttpOnly Cookie）、A-01・A-02を除き認証必須
エラー形式{"detail": "メッセージ"}（総論7.1節）。バリデーションエラーはFastAPI標準の422形式をそのまま返す
ID表現レスポンスの id 系フィールドはすべて文字列（BIGINTの精度落ち防止、総論2.4節）
日時表現UTCのISO 8601（Z付き）
一覧のページネーション{"items": [...], "total": 件数, "page": ページ番号}。pageは1始まり、1ページ20件を既定とする
欠番A-32（AIエージェントの応答生成は内部処理のためAPI非公開。基本設計書7章）

A-02GET /api/auth/callbackクエリ: code, state302リダイレクト（/、Cookie発行。失敗時は/login?error=<種別>、総論7.2節）
A-03POST /api/auth/logoutなし{"ok": true}
A-04GET /api/auth/meなし{"id","email","name","picture_url","role"}

4.3 チャンネル・メッセージ（A-05〜A-15, A-46〜A-49, A-69, A-71）

A-05 GET /api/channels（参加中＋参加可能一覧）

// response 200
{ "joined": [ { "id": "42", "name": "開発相談", "topic": "...", "is_public": true,
    "created_by": "7", "created_at": "...", "unread_count": 3 } ],
  "joinable": [ { "id": "50", "name": "総務問い合わせ", "topic": null, "is_public": true,
    "created_by": "3", "created_at": "..." } ] }

unread_countはjoinedのみに含まれる（未読バッジ用。T-22 read_states、基本設計書6.2節「設計判断」）。自分以外が送った、スレッド返信ではない発言のうち、既読時刻（無ければ参加時刻）より後に投稿されたものの件数。

A-69 POST /api/channels/{id}/read（既読化）

POST /api/channels/42/read
// response 200: { "channel_id": "42", "read": true }

T-22 read_statesのlast_read_atを現在時刻へ更新する（無ければ新規作成）。フロントエンドはS-03表示中（マウント時・新着メッセージ受信時）に呼び出す。専用の既読ボタンは無い。

A-07 POST /api/channels（チャンネル作成）

// request
{ "name": "経理連絡", "topic": "経理部からの連絡用", "is_public": true }
// response 201
{ "id": "42", "name": "経理連絡", "topic": "経理部からの連絡用", "is_public": true,
  "created_by": "7", "created_at": "2026-08-21T01:00:00Z" }

作成者は同一トランザクション内でT-03へ is_channel_admin=true として登録する。name は空文字不可・256文字まで。既存名との重複は409。

A-71 PUT /api/channels/{id}（チャンネル名・説明文の編集）

{ "name": "開発相談（改称）", "topic": "デプロイ・環境構築の相談窓口" }
// response 200: A-07と同じ形（更新後のチャンネル情報）

name・topicいずれも省略可（指定したフィールドのみ更新）。nameはA-07と同じ制約（空文字不可・256文字まで・既存名との重複は409）。topicに空文字を送ると説明文を削除する操作として扱いNULLにする。当該chadmin/adminのみ実行できる。

A-09 DELETE /api/channels/{id}（チャンネル削除）

DELETE /api/channels/42
// response 204

当該chadmin/adminのみ実行できる。参加者（T-03）・発言（T-05）・メッセージブロック（T-07）・送信予約（T-18）・AI設定（T-08）・AI利用ログ（T-13）・既読状態（T-22）はいずれもchannels(id)へのON DELETE CASCADEで連動削除される。取り消せない操作のため、フロントエンドは削除対象のチャンネル名の再入力を確認手段とする（S-06「チャンネル管理者」タブ）。

A-08 POST /api/channels/{id}/members（参加・招待。F-34）

// 公開チャンネル: 本人を追加（本文なし）
POST /api/channels/42/members
// 非公開チャンネル: 対象を指定して追加（呼び出し元は既存参加者であること、総論5.4節）
{ "user_id": "15" }
// response 201
{ "channel_id": "42", "user_id": "15", "is_channel_admin": false, "joined_at": "..." }

非公開チャンネルで本文の user_id を省略（自己参加）した場合は403。公開チャンネルで他者の user_id を指定した場合も403（本人のみ自己参加可）。非公開チャンネルの非参加者が呼び出した場合は存在を伏せるため404。参加者の追加に成功すると、同一トランザクション内でT-05へsender_type='bot'・bot_display_name='システム通知'の発言「（氏名）さんが参加しました。」を1件作成する（F-43。基本設計書6.2節「設計判断」）。招待の場合は追加された本人の氏名を使う（招待した人ではない）。

A-46 GET /api/channels/{id}/members（参加者一覧。補足03）

// response 200
{ "items": [
    { "id": "15", "name": "田中 智子", "email": "tanaka@kogasoftware.com", "picture_url": null,
      "role": "member", "is_active": true, "is_channel_admin": true, "joined_at": "2026-08-19T01:00:00Z" }
  ] }

対象はチャンネル参加者全員（require_channel_memberで保護。無効化されたアカウントも一覧に残り、is_active:falseで示す）。roleはグローバルなロール（システムadminバッジ表示用）、is_channel_adminはこのチャンネルのchadminかどうか。補足03メンバー一覧のほかS-06チャンネル管理者タブの追加候補選定、F-39の同姓同名判定でも共有する。

A-11 POST /api/channels/{id}/messages（メッセージ投稿）

// request（@田中 智子をF-41のオートコンプリートで選択した例）
{ "body": "@Kogack AI デプロイ手順を教えて／@田中 智子 さんも確認お願いします",
  "thread_parent_id": null,
  "mentions": [ { "target_user_id": "15", "display_name_snapshot": "田中 智子" } ] }
// response 201（即時。AI応答は非同期で別途投稿される、総論9.2節）
{ "id": "10301", "channel_id": "42", "sender_type": "human", "sender_user_id": "7",
  "body": "@Kogack AI デプロイ手順を教えて／@田中 智子 さんも確認お願いします",
  "blocks": [ { "block_type": "mention", "payload": { "target_user_id": "15", "display_name_snapshot": "田中 智子" }, "sort_order": 0 } ],
  "created_at": "2026-08-21T01:05:00Z" }

body は1〜4000文字。mentionsは任意（F-41のオートコンプリートで確定した人間へのメンションのみを含み、AIへのメンションは含めない）。各要素はtarget_user_idが当該チャンネルの参加者であることをAPI側で検証し、1件につきT-07 message_blocksへblock_type='mention'の行を1件作成する。投稿後、サーバーは(1) 本文中の@チャンネルAI名を検知→services/ai_agent.py を非同期起動、(2) services/trigger_matcher.py による自動応答トリガー判定を同期実行、の2処理を行う（基本設計書8.1節・総論9.3節）。人間へのメンション（mentions配列）はAI起動・トリガー判定のいずれの契機にもならない。

A-10 GET /api/channels/{id}/messages（履歴取得）

GET /api/channels/42/messages?since=2026-08-21T00:00:00Z&limit=50
// response 200
{ "items": [ { "id":"10301", "sender_type":"human", "sender_user_id":"7", "body":"...",
    "generation_status": null, "thread_reply_count": 2, "blocks": [], "created_at":"..." } ],
  "has_more": false }

since 省略時は直近50件。ポーリング（3秒間隔）は直近ポーリング時刻を since として差分取得する（基本設計書9.1節）。generation_status が "generating" の行はAI発言が生成中であることを示す（AIサポート10.3節）。

A-12 DELETE /api/messages/{id}（メッセージ削除）

DELETE /api/messages/10301
// response 200: { "id": "10301", "deleted": true }

論理削除（T-05.deleted_at/deleted_by）。投稿者本人またはadminのみ実行できる。チャンネル・DMどちらの発言、スレッド返信・元発言のいずれも同じエンドポイントで扱う。削除に成功すると以後A-10/A-18/A-13の一覧から除外される（元発言を削除した場合、そのスレッドのA-13/A-14は404になる）。参加していない会話の発言に対しては存在自体を伏せるため404、参加しているが投稿者本人でもadminでもない場合は403を返す（総論5.3節と同じ使い分け）。

A-13 GET /api/messages/{id}/thread（スレッド内の返信一覧）

// response 200
{ "items": [ { "id": "10305", "channel_id": "42", "dm_id": null, "thread_parent_id": "10301",
    "sender_type": "human", "sender_user_id": "15", "body": "@田中 智子 確認しました",
    "generation_status": null, "blocks": [ { "block_type": "mention",
      "payload": { "target_user_id": "7", "display_name_snapshot": "田中 智子" }, "sort_order": 0 } ],
    "created_at": "..." } ] }

古い順。A-10と同じくblocksを含む（F-41）。

A-14 POST /api/messages/{id}/thread（スレッドへの返信投稿）

{ "body": "@田中 智子 確認しました",
  "mentions": [ { "target_user_id": "7", "display_name_snapshot": "田中 智子" } ] }
// response 201: A-11と同じ形（channel_id/dm_idは元発言から継承、blocksを含む）

mentionsはA-11と同じ扱い（対象がチャンネル参加者であることを検証してT-07へ保存）。元発言がDMの場合はメンション候補元（A-46）が存在しないためmentionsを送っても無視され、blocksは常に空になる。

A-49 PUT /api/channels/{id}/visibility（公開/非公開切替）

{ "is_public": false }
// response 200: { "id": "42", "is_public": false }

4.4 DM（A-16〜A-19, A-70）

A-16 GET /api/dms（参加中DM一覧）

// response 200
{ "items": [ { "id": "9", "members": [ { "id": "15", "name": "田中 智子", "picture_url": null } ],
    "created_at": "...", "unread_count": 2 } ] }

membersは自分以外の参加者（アイコン・氏名解決済み）。unread_countはA-05のjoinedと同じ考え方（T-22 read_states、基本設計書6.2節「設計判断」）。

A-70 POST /api/dms/{id}/read（既読化）

POST /api/dms/9/read
// response 200: { "dm_id": "9", "read": true }

A-69と同じ（対象がdm_idになるのみ）。フロントエンドはDM会話画面表示中に呼び出す。

A-17 POST /api/dms（DM開始・グループDM対応）

// request（自分以外の相手user_idを配列で指定。1件でも複数件でもよい）
{ "user_ids": ["15", "23"] }
// response 200 or 201
{ "id": "9", "member_user_ids": ["7","15","23"], "created": false }

呼び出し元ユーザーを加えた参加者集合が既存のT-17と完全一致するT-04があれば created:false で既存DM（200）を返し、無ければ新規作成（201、created:true）する（基本設計書6.2節「設計判断」）。

4.5 検索・添付ファイル（A-20〜A-22, A-61, A-68）

A-20 GET /api/search（横断検索。詳細は6章）

GET /api/search?q=デプロイ%20手順&type=all&page=1
// response 200
{ "counts": { "message": 4, "file": 1, "document": 2 },
  "items": [
    { "type": "message", "message_id": "10245", "channel_id": "42", "channel_name": "開発部",
      "sender_display_name": "田中", "excerpt": "デプロイ手順は...", "posted_at": "..." },
    { "type": "file", "attachment_id": "301", "file_name": "デプロイ手順書.pdf", "channel_id": "42", ... },
    { "type": "document", "doc_title": "運用ドキュメント：デプロイ手順書", "doc_url": "...", "excerpt": "..." }
  ], "page": 1 }

// F-42: モディファイア付き検索（in:開発相談 from:田中智子 after:2026-08-01 デプロイ 手順）
GET /api/search?q=デプロイ%20手順&in=42&from=15&after=2026-08-01&type=all&page=1
// response 200（typeにdocumentを含めてもcountsのdocumentは常に0。6.5節）
{ "counts": { "message": 2, "file": 0, "document": 0 },
  "items": [
    { "type": "message", "message_id": "10245", "channel_id": "42", "channel_name": "開発部",
      "sender_display_name": "田中 智子", "excerpt": "デプロイ手順は...", "posted_at": "2026-08-19T01:06:00Z" }
  ], "page": 1 }

クエリパラメータ: in=channel_id、from=user_id、with=user_id、before/after/on=YYYY-MM-DD、during=YYYY-MM。いずれも省略可・複数同時指定可（AND）。in/withは指定した対象に自分がアクセス権を持たない場合（未参加チャンネル・未参加DM）、総論5.3節と同じ扱いで結果0件を返す（403にはしない。存在の有無を教えないため）。

A-68 GET /api/users（利用者検索。F-42・F-05）

GET /api/users?q=田中&limit=20
// response 200
{ "items": [
    { "id": "15", "name": "田中 智子", "email": "tanaka.dev@kogasoftware.com", "picture_url": "..." },
    { "id": "31", "name": "田中 智子", "email": "tanaka.soumu@kogasoftware.com", "picture_url": "..." }
  ] }

氏名（name）・メールアドレス（email）の部分一致（ILIKE）で検索し、is_active=trueの利用者のみを返す。q省略時は全利用者を氏名順で返す（limit件まで）。表示名が重複する利用者（上記の「田中 智子」2名）はどちらも候補に含め、区別はメールアドレスの併記で行う（F-39と同じ考え方）。補足02（DM相手選択）・S-05検索モディファイア（from:/with:）のオートコンプリート双方から呼び出す共通API。

6. 検索処理詳細

6.1 検索対象と権限フィルタリング

S-05横断検索（F-06、A-20）は3種類の結果を横断的に検索し、いずれも利用者の参照権限の範囲に限定する。

種別検索対象権限フィルタモディファイア対応（F-42）
メッセージT-05 messages.body（deleted_atがNULLの行のみ）参加中のchannel_id（非公開含む）とdm_idに限定（T-03/T-17との結合）in/from/with/before/after/on/during すべて対応
ファイルT-06 message_attachments.file_name同上（親メッセージの参加者限定を継承）同上（親メッセージのchannel_id/dm_id/sender_user_id/created_atを継承）
ドキュメント根拠Drive文書索引（基本設計書8.2節と同じ索引データ）質問者本人のGoogle Drive閲覧権限を都度確認（基本設計書8.2節と同一ロジックを流用）非対応。モディファイアを1つ以上含む場合は検索対象から除外（6.5節）
設計判断（ドキュメント検索の範囲はチャンネルのT-10に縛らない）: AIのチャンネル質問応答（F-19）はそのチャンネルのT-10（参照ドキュメント範囲）に限定するが、S-05横断検索は特定チャンネルに紐づかない全社検索であるため、T-09に登録された全社の索引対象からユーザー個人のDrive閲覧権限のみで絞り込む。チャンネルごとの参照範囲設定はAIの回答根拠を絞るためのものであり、人間による検索の可視性を制限する目的の設定ではないと整理する。

6.2 メッセージ・ファイル検索のSQL方針

-- pg_trgm による部分一致（日本語形態素解析は導入しない。想定規模200名では要件定義書7章の
-- 目標値（2秒以内）を満たせると判断。将来語幹一致の精度が要求される場合はFTS導入を再検討）
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_messages_body_trgm ON messages USING gin (body gin_trgm_ops);
CREATE INDEX idx_messages_channel_created ON messages (channel_id, created_at);
CREATE INDEX idx_messages_dm_created ON messages (dm_id, created_at);

SELECT m.* FROM messages m
LEFT JOIN channel_members cm ON cm.channel_id = m.channel_id AND cm.user_id = :me
LEFT JOIN direct_message_members dm ON dm.dm_id = m.dm_id AND dm.user_id = :me
WHERE m.deleted_at IS NULL
  AND (cm.user_id IS NOT NULL OR dm.user_id IS NOT NULL)
  -- キーワード: 引用符なしの各語をAND結合、"…"はフレーズのまま1条件（6.5節）
  AND m.body ILIKE '%' || :term1 || '%'
  AND m.body ILIKE '%' || :term2 || '%'
  -- モディファイア（指定されたもののみ条件を追加。6.5節のパース結果に応じてSQLを動的に組み立てる）
  AND (:in_channel_id IS NULL OR m.channel_id = :in_channel_id)
  AND (:with_user_id IS NULL OR dm.dm_id IN (SELECT dm_id FROM direct_message_members WHERE user_id = :with_user_id))
  AND (:from_user_id IS NULL OR m.sender_user_id = :from_user_id)
  AND (:after_date IS NULL OR m.created_at >= :after_date::date + interval '1 day' AT TIME ZONE 'Asia/Tokyo')
  AND (:before_date IS NULL OR m.created_at < :before_date::date AT TIME ZONE 'Asia/Tokyo')
  AND (:on_date IS NULL OR m.created_at >= :on_date::date AT TIME ZONE 'Asia/Tokyo'
                        AND m.created_at < :on_date::date + interval '1 day' AT TIME ZONE 'Asia/Tokyo')
  AND (:during_month IS NULL OR m.created_at >= (:during_month || '-01')::date AT TIME ZONE 'Asia/Tokyo'
                              AND m.created_at < (:during_month || '-01')::date + interval '1 month' AT TIME ZONE 'Asia/Tokyo')
ORDER BY m.created_at DESC
LIMIT 20 OFFSET :offset;

ファイル検索（T-06）も同じ考え方で、message_attachmentsをmessagesに結合してchannel_id/dm_id/sender_user_id/created_atを継承し、同一のモディファイア条件を適用する（file_nameに対してILIKE、in/with/from/日付系はJOIN先messagesの列で判定）。

6.3 ドキュメント検索・索引の実装

基本設計書8.2節の索引（S-08「今すぐ同期」A-41で実行）を検索にも流用する。索引テーブル（例: doc_index、T-xxを新設せず内部実装として保持してよい）にドキュメントID・フォルダパス・抜粋・埋め込みベクトルを保持し、質問文/検索語のベクトル類似度で候補を絞ったのち、候補ごとにdrive_client.pyでユーザー本人のDrive閲覧権限をそのつど確認して除外する（基本設計書8.2節と同一の2段構成）。

6.4 タブ・件数・ページング

S-05の「すべて/メッセージ/ファイル/ドキュメント根拠」タブは、A-20が一括で返すcountsをもとにフロントで切替表示する（タブ切替のたびに再検索はしない。初回検索でtype=allとして3種すべてを取得）。1タブあたりの表示件数上限は20件、超過分は「もっと見る」でtype指定の追加リクエスト（type=message&page=2等）を行う。モディファイア（in/from/with/before/after/on/during）を1つ以上含む場合、ドキュメント根拠タブは無効化表示（グレーアウト＋「検索条件は発言・ファイルのみに対応」の注記）とし、counts.documentは常に0を返す（F-42、6.5節）。

6.5 F-42 検索条件モディファイアのパース方式

フロントエンドのトークン分解: 検索欄の生文字列を正規表現 /(in|from|with|before|after|on|during):(\S+)/g で走査してモディファイアのトークンを抽出し、"…"で囲まれた区間はフレーズトークンとして別扱いにする。残りの空白区切り語は自由語トークンとする。in:/from:/with:のトークンを検出すると、直後に候補ポップオーバー（in:はA-05で取得済みの参加チャンネル一覧から前方一致、from:/with:はA-68を都度呼び出して氏名・メールアドレスの部分一致）を表示し、候補を選択すると当該トークンをid（channel_id／user_id）に確定する。確定前に検索を実行した場合、フロントは値をチャンネル名／氏名の文字列としてそのままA-20へ渡し、バックエンドはchannel_id/user_idへの解決を試みたうえで一致しなければ0件を返す（曖昧一致は行わない。基本設計書5.20節のF-39と同じく、氏名の完全一致でも複数候補があり得るため）。

バックエンドのクエリ組み立て: services/search.pyのbuild_search_query(params)が、A-20で受け取った構造化パラメータ（in/from/with/before/after/on/during/q）から6.2節のSQLテンプレートへバインドするパラメータを組み立てる。qはサーバー側でも"…"の有無を再度パースし（フロントのバリデーションを信頼しない）、フレーズはエスケープしてそのまま1つのILIKE条件に、自由語は空白分割してそれぞれ独立したILIKE条件にする（AND結合。6.2節）。モディファイアが1つ以上存在する場合、type=documentのリクエストであっても常にcounts.document=0・itemsにdocumentを含めない応答を返す（6.1節・6.4節）。

設計判断（サーバー側でqを再パースする理由）: A-20はcrypto等の認可を経ないGETリクエストであり、フロントのトークン分解ロジックをバイパスして直接クエリパラメータを叩くことも可能。qに含まれる引用符の解釈をサーバー側で信頼せず独自に再パースするのは、フレーズ検索の意味（完全一致か部分一致か）がリクエスト送信者の自己申告に依存しないようにするため（改ざんされても結果の意味が変わるだけで、権限上の問題は生じないが、検索結果の一貫性を担保する目的）。in/from/withについても同様にidの形式（数値）のみを受け付け、それ以外の値は無視する（400にはしない。UIの軽微な不整合でエラー画面に落ちるより、条件が無視されて広めの結果が返るほうが利用者体験として穏当なため）。
